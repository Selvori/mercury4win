# 项目记录入口

项目采用与代码一起版本管理的 Markdown 记录。聊天用于沟通，已确认且后续需要复用的信息落入以下文件；不依赖某个聊天窗口或个人电脑目录。

| 记录 | 内容与维护方式 |
| --- | --- |
| [STATUS.md](STATUS.md) | 当前状态、当前验证基线、下一步；更新替换，不积累长篇历史 |
| [ISSUES.md](ISSUES.md) | 问题与尚未移植能力的唯一状态台账，稳定编号与关闭条件 |
| [DECISIONS.md](DECISIONS.md) | 已接受的长期约定、理由与影响；变更时新增记录并注明替代关系 |
| [WORKLOG.md](WORKLOG.md) | 按实质任务追加日期、变更、验证、遗留事项与相关编号 |
| [TESTING.md](TESTING.md) | 固定样例登记、可重复验收步骤、验证记录模板 |
| [audits/](audits/) | 按日期保留的审查证据与专项验证报告；状态变化回写台账 |
| [../AGENTS.md](../AGENTS.md) | 对后续协作持续生效的工程与记录规则 |

## 每次任务的最小流程

1. 开始：核对工作目录和 Git 状态，读 STATUS；按任务需要读相关问题、决策和测试约定。
2. 执行：新问题先查重再编号；明确区分用户要求、已验证事实和待验证推断。复杂问题详情可独立成报告，台账引用它。
3. 验证：记录真正执行的命令或用户路径、结果、平台和限制；外部站点不稳定与本地回归分开记录。
4. 结束：追加一条 WORKLOG；有变化才更新 STATUS / ISSUES / DECISIONS。交付说明引用记录，不复制整份报告。

文档中的文件位置用于导航，代码可能移动；证据还应保留提交或工作区基线。记录已有未提交改动时说明是工作区结果，不能冒充某个提交的结果。

## 状态与证据

- 问题状态：待处理 → 处理中 → 待验证 → 已关闭；受阻必须写清阻塞及恢复条件，延期必须写明理由。取消 / 不采用保留编号与原因。
- “静态确认”说明已核对代码；“已复现”说明有实际失败案例；二者都不等于已经修复。
- 不以编译通过代替桌面、数据库或流式任务验收。验收条件范围内有未完成项时，不能关闭问题。
- 同一事实只设一个维护位置：当前问题状态在 ISSUES，历史证据在报告，任务经过在 WORKLOG。其他文档引用它，不另建冲突的 TODO 清单。
- 日期使用 `YYYY-MM-DD`（本项目协作时区 Asia/Shanghai），文本使用 UTF-8。实质改动更新记录，避免无信息增量的流水账。
- 用户要求优先于文档。发现文档与代码不符时先核实并记录差异，不依据陈旧记录进行破坏性操作。
